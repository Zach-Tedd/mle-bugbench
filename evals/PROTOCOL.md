# Evaluation protocol: do AI assistants catch ML leakage?

**Question:** when asked to work on leaky ML code, do AI coding assistants catch the leak from the data and code alone, and how much do the generator's source, the scenario's framing, or an explicit request to review add?

## Conditions

| Condition | What the assistant is told |
|---|---|
| `realistic` | A preview of the data (size, column types, first rows, summaries) and the model code, then "Please improve the model…". No generator source, no scenario, no claimed score. Helper functions a solution needs (t05's `candidate_subsets`) are included without the data loader. |
| `blind` | Only the code and the interface, then "Please improve the model…". No scenario, no claimed score, module docstrings removed. |
| `neutral` | The scenario, then "Please improve this model and give me the complete updated solution.py." No hint that anything is wrong. |
| `review` | The scenario, then the task's review instruction: "Review it, fix every problem that makes the reported performance untrustworthy…" |

All three prompts include the same `data.py`, starter `solution.py` and interface table, and are generated by `bugbench.prompt`. In `blind` and `neutral`, the interface table describes `notes` neutrally. A test checks that no blind prompt contains the scenario or cue words such as "publish", "bug" or "leak".

**Why `blind` was added:** in session A, ChatGPT passed all six tasks under `neutral`. The neutral scenario still states a suspiciously high score and pressure to publish, which can prompt scrutiny by itself. `blind` was added before sessions B and C so the three assistants stay comparable; ChatGPT's blind runs were collected after its other runs.

**Why `realistic` was added:** in session B, Claude's notes quoted values that exist only in `data.py`'s source ("+2.5*label", "SD 3"), and ChatGPT's blind t06 answer described the county-specific signal in f3. Every earlier prompt included the generator's source code, which shows exactly how each bug was planted. Real engineers see data, not the code that generated it. Results from `blind`, `neutral` and `review` therefore measure detection *with the generator visible*; `realistic` measures detection from the data and model code alone.

## Rules for every run

1. **New chat for every run.** No memory, custom instructions or files from earlier chats. Turn off memory or personalisation if the app has it.
2. **Paste the prompt exactly** as generated: `uv run python -m bugbench.prompt t01 neutral | clip.exe`, then paste.
3. **One turn only.** No follow-up questions, no "are you sure?", no retries. Whatever comes back first is the answer.
4. **Default settings.** Use the app's default model unless the run is about a specific model; no extra tools enabled beyond the defaults.
5. **Take the first complete Python code block** that defines `run(...)`, unchanged, and save it as `evals/runs/<assistant>/<task>_<condition>.py` (for example `evals/runs/claude/t01_neutral.py`).
6. **If there is no usable code block**, save a file containing only `raise RuntimeError("no code returned")`, so the run counts as a failure rather than disappearing.
7. **Read the code before grading.** It is model-written and runs with your permissions.
8. **Record the run** in `evals/runs/<assistant>/meta.json`: the model name shown in the app, the interface (web/desktop app), and the date.

```json
{"model": "<name shown in the app>", "interface": "web chat", "date": "2026-11-20"}
```

## Grading

```bash
uv run python -m bugbench.evaluate     # writes evals/results.csv and evals/results.md
```

Each answer is graded in its own process with a 15-minute limit. A crash or timeout scores 0 and is recorded as an error.

## What this can and can't show

- One run per cell, at default settings: assistants are not deterministic, so a single pass or fail is an observation, not a rate. Repeat runs are needed before claiming a rate for any one task.
- Results describe the models and app versions on the recorded dates; they will change.
- The tasks are synthetic and their reference solutions are public, so a model may have seen similar material.

## Who reviewed failures

Grading is automatic. Every failure was then reviewed by reading the answer, to decide between a real miss and a grader flaw, with help from an AI assistant that is itself a Claude model. Because Claude is also one of the assistants evaluated, every grader change is a general rule backed by regression tests covering both ChatGPT's and Claude's answers, and none is specific to one model's output.

## Grader changes made during evaluation

| When | Change | Triggered by |
|---|---|---|
| Pilot (t01) | Accept standard metric names (`average_precision`); allow retried duplicates inside the test set; compare positive rates on unique rows | ChatGPT, both conditions |
| Session A (t03) | Accept ROC-AUC computed per patient | ChatGPT, neutral and review |
| Session B (t03, t06) | Find the metric name anywhere in a qualified label, in any word order (`roc_auc_patient_level`, `roc_auc_leave_one_county_out`). The Session A rule accepted only a leading qualifier, which matched ChatGPT's wording but not the same idea worded differently | Claude, 4 answers |
